# 众生绘卷

给《众生之门》美术组使用的任务平台。纯静态前端，部署到 GitHub Pages；Supabase 负责邮箱登录、成员权限、任务及 Realtime。

打开本地预览：在本目录运行 `python3 -m http.server 4173`，访问 http://localhost:4173 。配置未填写时进入明确标记的本地演示；身份切换仅存在于演示模式。真实模式无示例数据。

## 上线（需要自己的仓库和 Supabase 项目）
1. 将本目录内容放到一个 GitHub 仓库根目录，默认分支 main；仓库 Settings → Pages → Source 选择 GitHub Actions。
2. 在新 Supabase 项目 SQL Editor 执行 supabase/schema.sql 一次。此脚本新建 guild_ 前缀表、权限和 Realtime publication；已有项目请先审查同名对象。
3. 填 config.js 的 Supabase URL、publishable/anon 公钥。不要填 service_role 或数据库密码。
4. Supabase Authentication 的 Site URL 和 Redirect URLs 填实际 GitHub Pages 地址（包括仓库子路径及结尾斜杠）。配置可用邮件发送服务；OTP 登录也支持邮件内链接。
5. 先登录自己的邮箱，再按 schema.sql 末尾示例将自己的用户 ID 设置为负责人。其他成员登录后，由负责人在数据库按 ID 开通并设置昵称。仅已开通成员可查看团队数据。
6. 推送 main 后 Actions 部署。使用两个不同账号和浏览器，验证一人认领、另一人即时看到更新；交稿后由其他负责人验收。检查重复认领仅一人成功，重复审核仅记一笔积分。项目未连接前无法验证真实邮件、RLS 和 Realtime。

## 当前范围
- 发布任务、分类和状态筛选、搜索、认领、归还、作品链接交稿、历史版本和反馈、退修再交、验收、累计榜和本月榜。
- 同一任务使用数据库行锁串行处理；已完成任务不再允许审核。贡献分来自发布时约定的工作量，验收记分只发生一次。禁止验收自己的任务。排行不是画技评分。
- Realtime 收到变更后重新读取；重新连接、窗口重新获得焦点也会补读。连接状态有明确提示。演示使用本地存储事件跨标签同步，不是多人联网。
- 所有已开通成员能看交稿链接；请确保分享链接适合团队内查看。暂用网盘/作品链接，不包含原图上传、站内聊天、成员管理 UI、任务删除和修改。
- 页面使用灵力图谱的苔绿、米白、暖棕和平涂轮廓，延续众生之门会馆与同人创作语境。插画为程序绘制的原创装饰，没有复制官网画师作品。

## 历史卡牌记录
- 已有数据库升级时只运行 `supabase/002_import.sql`，不要重跑初始化脚本。新项目先运行 `schema.sql` 再运行增量脚本。
- 原表记录以卡牌 ID 生成唯一导入键，重复导入跳过已有记录，不覆盖平台上的修改。旧版参考与灵卡分开保留。原始行号、画师、进度和单元格存入 `source_record`。
- `imported` 表示待负责人确认，贡献分为空，不能直接认领或验收。原表的卡牌消耗不作为贡献分；“已递交终稿”不视为平台验收。
- 负责人打开详情，填写已约定的贡献分，核对并选择已开通的画师账号。原表有画师时必须绑定账号，旧版参考还需要确认是否单独绘制。确认后转为创作中；未指定画师的新任务转为待认领。
- 已交终稿也须补交作品链接，经过其他负责人验收后才记分。“原表交稿记录”来自原表登记，与平台贡献榜分开展示。
- 原表文件和批量导入 SQL 不提交到公开仓库，仅通过数据库的既有成员权限展示数据。

## 负责人工作台与阶段奖励
已有数据库依次执行 `002_import.sql`、`003_admin_tasks.sql`。第二个增量支持负责人发布 / 分配任务、修改未认领任务、管理画师昵称与开通状态，并将贡献记录关联到实际验收版本。它保留原有登录、RLS 与 SMTP 配置。

工作台可查看暂行分值表，分类建议分 × 复杂度（0.75 / 1 / 1.25），取整到 5 分。分值对应完整交付物；创作开始后禁止修改任务分值。草稿、线稿、上色及合理修改不重复计分，多人拆项需由负责人核对总分预算。

第一期奖金总额 100 元，并列第一均分。统计期为北京时间 2026-10-29 00:00 至 2027-01-01 23:59:59（已在数据库 guild_campaign 设置）。负责人可用工作台公布北京时间起止时间。本期成绩根据验收版本的提交时间筛选，而不是验收时间；逾期验收可以补记，最终通过版本在截止后提交则不计入本期。排名为暂列，最终名单需人工核对，不自动支付奖金。累计贡献独立保留。

## 金山原表自动同步
金山「全部卡牌」是卡牌资料的唯一来源，网站约每 5 分钟同步一次；任务认领、交稿、验收和贡献分只在平台内发生。

链路：pg_cron（`guild-kdocs-sync`）→ Edge Function `kdocs-sync`（`x-sync-secret` 鉴权）→ 金山 AirScript 共享脚本（`supabase/airscript/sync-cards.js`）→ `guild_kdocs_apply` → `guild_kdocs_cards` 镜像 → `guild_tasks` / `guild_task_preview`。

- 卡牌以 K 列「同步ID」识别，不依赖行号；脚本只会给空白的同步ID 补值。请勿修改或复制 K 列（复制会造成重复 ID，同步会停下等待修正）。
- 未启用卡（原表登记）：名称、说明、类型、原表画师和完成情况自动更新。
- 已转正式任务：只更新原表登记信息；名称或说明的改动挂起为「原表有更新」，由负责人决定采用（仅待认领任务）或保持原要求。分值、画师、状态从不被同步改写。
- 原表删除：只标记 `source_removed_at`，不删除任何记录。未启用卡对游客隐藏、不能被确认成任务；正式任务、作品和贡献分保留并提示核实。原表恢复同一行（同步ID 不变）即重新显示。
- 保护：读取不完整、表头改动、重复 ID 会整体拒绝；一次移除超过 max(5, 10%) 或新增超过 max(10, 25%) 张会暂停，负责人在网站摘要条核对后点「确认」（或 SQL：`select guild_kdocs_approve(<移除数>, <新增数>);`）。失败不改动已有数据。
- 列表：金山表的卡按登记进度并入平台列表——尚未分配 → 待认领，已登记画师 → 创作中，已递交终稿 → 待验收（仅显示；仍需负责人定分并绑定画师账号后才能认领和记分）。已从金山表移除的卡不出现在任何列表。
- 默认分值与 DDL：金山表的卡默认 20 贡献分、期望交稿 2026-11-15（`010_card_default_points_due.sql`；新卡读取 `guild_kdocs_state.default_points / default_due_date`）。预设分值只在负责人定分发布、验收通过后才会记入贡献；同步不会覆盖负责人改过的分值和日期。
- 未注册画师：金山表登记了画师的卡，定分发布时可直接按表格名字发布（显示「名字（未注册）」）。负责人可代交稿进入待验收；画师注册后在任务里「绑定账号」，该名字下的任务一并转到账号，之后才能验收记分（`011_unregistered_artists_and_proxy_submit.sql`）。
- 稿件展示：已完成、待验收作品和金山表已交终稿的卡，每张都署名（游客也能看到署名，作品原图需登录）。
- 删除：负责人可在工作台或任务详情里删除自己手动发布、还没人认领、没有贡献分记录的任务；它的交稿（如测试稿）和上传图片一并删除（`008`、`009_admin_delete_with_submissions.sql`）。存储策略只允许删除所属任务已不存在的图片。金山表里的卡请在金山表里删除。
- 状态：`guild_kdocs_state.last_success_at`、`guild_kdocs_runs`（保留 90 天，含 cards / changed / marked_missing / tasks_* 统计和失败代码）。
- 金山脚本令牌默认 180 天过期；过期后日志出现 `SOURCE_HTTP_401/403`，网站会给负责人提示，需要在金山重新生成令牌并更新 Supabase 的 `KDOCS_AIRSCRIPT_TOKEN`。

数据库升级顺序（已有项目）：`004` → `005` → `007` → 两次手动同步验证 → `006`（定时任务）。部署函数：`supabase functions deploy kdocs-sync --no-verify-jwt`。测试：`node tests/kdocs-postgres.test.mjs`（需要一次性本地 PostgreSQL）、`node tests/frontend-filters.test.mjs`、`node --experimental-strip-types tests/edge-function.test.mjs`、`node tests/kdocs-normalize.mjs`、`node tests/airscript-sync.cjs`。
